## How it was committed

The work landed in one working tree alongside earlier uncommitted changes (account
expiration, avatars, auth tweaks) and a parallel session's Lists/Requests feature. Because
those touch the same files, commits are grouped **by file**, not strictly by feature — a
commit's message says what it mainly contains, and some files carry more than one change.

Because of that, an individual commit on the branch may not build on its own (an earlier
commit can import a file that arrives in a later one). The PR is therefore merged with
**Create a merge commit**: `main`'s first-parent history stays one buildable step, while
the branch keeps the readable breakdown for `git log release-1.0` / blame. Future PRs are
small and use Squash and merge, per RELEASING.md.

## Decisions

**Versioning.** Semantic versioning starting at 1.0.0. One source of truth: the three
`package.json` files, kept in step by `npm run release:version -- X.Y.Z`; the server reads
its version from `backend/package.json` (no more hard-coded numbers). The git tag must match
or the release workflow refuses to publish.

**Distribution.** Pre-built multi-arch images (amd64 + arm64) on GHCR at
`ghcr.io/oddomens/plinthio`, tagged `X.Y.Z`, `X.Y`, `X` and `latest`. Users install by
downloading only `docker/docker-compose.yml`; they pick an update channel with
`PLINTHIO_TAG`. Building from source moved to `docker/docker-compose.build.yml`. Chosen
over "clone and build" because it is one command to install and one to update, and works on
ARM boxes without a toolchain.

**Upgrade safety.** Before a new version's first start, the server snapshots the database
(`config/backups/plinthio-backup-before-<new>-from-<old>-….sqlite`) using a migration-free
connection. The last-run version is kept in `config/.version` because it must be read
before the database is opened.

**Update notifications.** The server (not the browser) polls GitHub's "latest release"
endpoint on start and every 12 h, anonymously; `UPDATE_CHECK=false` disables it. Only
admins can read the result. The banner is dismissed per version and the dismissal is stored
in the admin's preferences so it syncs across devices. Pre-releases are ignored by design,
which also gives a way to pull a bad release out of the banner (mark it pre-release).

**GPU passthrough off by default.** The `devices: /dev/dri` block in the compose file is
now commented out, because with it active `docker compose up` fails on machines without a
GPU device node — the most common first-install failure. Trade-off: Intel/AMD users must
uncomment it; the changelog calls this out.

**Video is not offered for offline download.** Files are multi-GB and usually need
transcoding; browsers don't reliably grant that much storage to a web app.

**Detail page before playback, for everything.** One page (`TitleView`, formerly the
manga-only `MangaView`) serves every media type, with a per-type vocabulary in
`frontend/src/utils/mediaVocab.js` (units, verbs, creator label, S1 · E5 episode labels).
Standalone titles get the same page as a "series of one". Readers and players open from
there; the shelf no longer plays anything directly (it keeps the manga reader only for
jumping to a bookmarked page).

**Every view shows series, never loose volumes (#14).** Since grouping into series now
happens in all four views, the default view was renamed from "Series" to **Alphabetical**
(its stored id stays `series` so saved preferences keep working). Disk Folders places a
series under the deepest folder all its titles share, so season folders don't split a show.
A custom folder holding some volumes of a series shows a card for just those volumes;
removing that card removes them all from the folder.

**Single titles vs. collections (#14).** A detail page lists its titles only when there's
more than one. A movie, standalone book or audiobook — or a "series" the library holds one
title of — gets a title page (details + one action). A collection such as Star Wars with
several movies keeps the list; that's the deciding rule, not the media type.

**Merging the ratings branch (#16).** It was written against pre-1.0 code, so the merge
had 10 conflicts, all resolved keeping both sides (e.g. a card shows your star rating and
its offline badge together; volume rows keep Download and gain Rate). Adapted to 1.0:
its `MangaView` changes were carried into the all-media `TitleView` (header "Rate S1 · E2"
etc. via `entryLabel`); `/api/ratings` now validates ids, respects parental controls
(an item above your limit 404s) and returns generic errors; queries gained the extras
filter alongside the new `user_ratings` join. A test pins the parental-controls case.

**How extras are recognised (#15).** `services/extras.js`, a pure function of the scanned
paths (unit-tested). Named extras folders and name suffixes (the common media-server conventions)
anywhere; for movie libraries also "a film's folder": the file named after the folder (or
the largest) is the film, everything in its subfolders is an extra, and loose siblings are
extras only if under 40% of the film's size — so a folder of full-length films (a
collection) is never collapsed. Shows only use the named folders/suffixes; their extras
take the show's series. Classification is re-applied to every item on each scan, extras
never get the folder poster or a TMDB match (a frame from the clip instead), and older
extras that already had the film's poster are re-arted.

**Collections: grouped by default, expandable (#15).** The shelf shows a movie collection
as one card; the "All movies" switch (remembered per device) lists each film. `/title/:id`
now always shows that one title — even inside a collection — with a "More in …" row;
clicking a film on a collection page opens it, while Watch still plays directly.

**Creators the scanner made up are hidden.** Without online metadata a video's creator is
its folder name; `realCreator()` in `mediaVocab.js` drops creators that just repeat the
title, and "Unknown Author", from display and from Creator grouping.

**Shelf views: Series, Creator, Disk Folders, Custom Folders.** "Grid" and "By Series"
merged into Series. Series and Creator can't be disabled; admins can switch off the two
folder views server-wide, users can hide views for themselves. Old stored names
(grid/author/series) map onto the new ones on both server and client.

**Skipped is its own state, not "read".** It's a separate `user_progress.is_skipped` flag
so read history and stats stay truthful; it counts toward series progress and next-volume
logic, and any real reading (or mark read/unread) clears it. Skipping a volume already
read does nothing — read wins.

**Kids Mode is allow-listed, not block-listed (#21).** A kids account sees nothing until
something is made kids-safe: a whole library, a series (including volumes added later) or
one title. Chosen over "hide these" so a new library or scan never exposes anything by
accident. It's enforced in the same SQL fragment as parental controls (`accessSql` in
`services/visibility.js`, formerly `ratingSql`), so every listing, file route, watch party
and sync API gets it for free; a content limit still applies on top. Admins can't be kids
accounts.

**Missing files are kept (#21).** A scan used to delete titles whose file vanished, which
took progress, ratings and list entries with it whenever a drive failed to mount. Now they
get `missing_since`, are hidden from everyone by the same `accessSql`, and are restored
automatically when the file returns. Removal is an explicit admin action in Library Health.

**Pause screens are an admin choice, default Details (#23).** The user asked for admin
options with "simple like now" as one. Details is the default because it's the new feature
and the least intrusive of the three new ones; admins who prefer the old behaviour pick
Simple. TMDB has no trivia endpoint, so "facts" means what TMDB does keep (budget, revenue,
original title/language, seasons, keywords…), fetched with the credits in the same request
(`append_to_response=…,keywords`). Credits cached before this are treated as stale once so
they pick the facts up.

**Skip amounts are per user (#23).** Stored in the user's preferences (`videoSkip`), so they
follow the person across devices; defaults back 10 s, forward 30 s. The arrow keys use them.

**PDFs render on the server (#24).** Client-side pdf.js was the first idea, but rendering
pages to cached JPEGs with poppler means the page reader, offline downloads, OPDS-PSE and
Mihon all get PDFs through the existing page API with no extra client code. poppler-utils
is GPL but is only run as a separate program; nothing links against it. mupdf was avoided
(AGPL).

**Sync apps sign in with API keys (#25).** Same model as OPDS: username plus a per-app key,
never the account password. Mihon's tracker sends no credentials, so the Komga API sets a
cookie tied to the key's id (deleting the key ends it). KOReader sends MD5(password), so keys
now also store an MD5; keys made before 1.0.0 must be re-created for KOReader. The Komga
DTOs were copied from the extension and tracker sources (keiyoushi `src/all/komga`, mihon
`data/track/komga`) rather than Komga's docs, since those two clients are what has to parse
them. KOReader EPUB positions (XPointers) can't be produced by Plinthio, so EPUB sync
towards KOReader only relays other KOReader devices; Plinthio takes the percentage.

**CSP on by default** with `CSP=off` / `CSP=report-only` escape hatches, since it could only
be verified in headless Chromium, not every browser/proxy combination.

## To do by hand

1. Review and merge the PR (**Create a merge commit** — see above).
2. Push the tag: `git checkout main && git pull && git tag v1.0.0 && git push origin v1.0.0`.
3. After the workflow finishes, set the GHCR package to **Public**
   (github.com/orgs/OddOmens/packages/container/plinthio/settings).
4. Own server: it runs a locally built image. Switch to the published image, and
   uncomment the `/dev/dri` lines in its compose file to keep hardware transcoding.
5. Optional: branch protection on `main` requiring CI.

## Follow-ups (not in 1.0.0)

- One user closing a video no longer stops others, but HLS jobs are still shared per item
  rather than per user — fine at household scale.
- Progress sync for audiobook apps — deferred (reader apps are done: Mihon, KOReader).
- No screen yet for intro/credits markers or for hiding a title from everyone; both are
  API-only (documented in docs/video.md and docs/accounts-and-access.md).
- Komga API loads the user's whole page-readable catalog per request and filters in JS;
  fine for households, worth an indexed query path for very large libraries.
- Opening `/series/<komga id>` from Mihon's "open in browser" lands on an empty page.
- Shared household lists — later.
- "New this week" notifications (webhook/ntfy) — later.
- Items still expose `path` to admins in list payloads; fine, but could move to detail-only.
